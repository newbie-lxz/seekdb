# 赛题四：全文索引热路径优化

## 范围与基线

以 `2026-competition` 分支的 `ebaea0dfa835c648248715a4327f9ebfa5f2ebaf` 为基线。
本次优化 IK 分词与各分词器共用的词频聚合路径，适用于建索引、
`TOKENIZE` 及查询词解析，不改变词典、分类边界、分词规则或 MATCH 语义。
官方 benchmark、输入数据、SQL、计时与评分文件均保持原样。

## 重复工作及修改

1. `ObFTCharUtil::do_classify` 原来依次调用分类辅助函数，每个辅助函数
   都解码同一个字符。中文字符需要经过英文字母、数字和中文三次解码，
   其他类别可能需要更多次。现在只解码一次，再按原先的优先级调用同一组
   Unicode 分类谓词。UTF-16 的代理项检查仍只适用于 UTF-16/UTF-16LE。
2. IK 主循环已获取当前字符地址、长度与分类，但四个处理器各自通过
   `process` 再读取上下文。现在把已获取的数据传给原来的虚函数
   `do_process`。处理器顺序、状态更新和错误传播保持原样。
3. `ObAddWord::groupby_word` 原来先查找词频，再调用覆盖写入；覆盖写入
   会再次计算哈希、遍历桶，并分配替换节点。现在使用现有的
   `set_or_update` 接口，命中时原地累计。保留原有首次插入计数为 1、
   后续增加 `word_freq` 的规则，以及排序规则等价时保留最后一个词形的行为。
   未启用聚合的路径保持原样。

## 正确性验证

新增 `fts_index.fts_hot_path` mysqltest，并加入 `psmalltest.py`：

- 对照完整 TOKENIZE 输出中的词、词频和文档长度；
- 包含重复词、大小写、全角字母/数字、中文、日文、韩文、补充平面字符、
  NUL/制表符，以及 IK smart/max_word 两种模式；
- 对照 MATCH 的文档 ID 和相关度；
- 对照 UPDATE、DELETE、INSERT 后的检索结果；
- 覆盖共用词频聚合路径的 space、beng、ik、ngram 和 ngram2 分词器。

另在本地把基线头文件与优化头文件同时编译到同一个对照程序中，比较
所有 Unicode 标量值在 UTF-8、UTF-16、UTF-16LE 下的分类，以及全部
16 位代码单元、空指针和部分异常字节序列。返回码与字符类别全部一致：
`PASS: 3471107 baseline/optimized classification comparisons`。

## 性能验证方法

在同一台虚拟机依次构建基线与优化版本，使用相同编译选项、服务参数和
未经修改的 `tools/benchmark/fts_large_bench.sh` 默认参数。构建时使用
`-O1 -g0 -DNDEBUG` 和 `-j3`，以适应本地约 4 GB 内存；因此本地耗时
不应与官方 CI 的冻结基线直接比较，也不能视为平台成绩。

```bash
LABEL=before OUTPUT=/path/to/before.txt bash tools/benchmark/fts_large_bench.sh
LABEL=after OUTPUT=/path/to/after.txt bash tools/benchmark/fts_large_bench.sh
```

每次运行均使用新的输出文件，默认重新建库、灌数、建索引。
比较三个建索引指标、两个分词指标和四个检索指标，并保留各项退化；
不能只用命中数证明查询正确，也不能把字符分类微基准的收益当成端到端收益。

基线和优化版本均已成功构建。新增 mysqltest 在优化版本上与基线记录逐字比较通过。
对默认 benchmark 数据集额外查询四组命中文档，分别得到 8001、11000、7332、9333 行，
按 ID 排序后的全部 ID 与保留 8 位小数的相关度逐字比较一致。第四组是 LIMIT 查询的
完整命中集；官方 LIMIT benchmark 自身返回 20 行。

运行测试的客户端为 MariaDB 10.11 的 `mysqltest`，测试文件内使用 `SET NAMES utf8mb4`。
当前基线 SQL 层不支持 `CONVERT(... USING utf16)`，因此 UTF-16/UTF-16LE 由上述
字符分类 C++ 对照覆盖，SQL 回归使用 UTF-8。

原始报告保存在 [fts-performance/results](fts-performance/results/)；首轮先基线后优化，
随后反向顺序各运行一次，检查实例启动顺序和 SQL 循环耗时波动。

## 本地结果

环境：Ubuntu 24.04 虚拟机，4 个 vCPU、约 4 GB 内存，seekdb
`memory_limit=2G`。两个版本使用相同配置、相同数据目录，逐次重新建库、灌数、建索引；
计时期间没有构建任务。编译器为随项目依赖提供的 Clang 17。

下表为每个版本两次完整运行的算术均值；分词和查询每次运行内部各有 3 个采样组。
改善率为 `(before-after)/before`，没有扣除 SELECT 1 或丢弃退化项。

| 指标 | 优化前 | 优化后 | 耗时下降 |
| --- | ---: | ---: | ---: |
| IK 双字段建索引（秒） | 17.66750 | 16.73950 | 5.25% |
| IK content 建索引（秒） | 13.80950 | 13.08050 | 5.28% |
| BENG 建索引（秒） | 7.24450 | 7.03600 | 2.88% |
| IK TOKENIZE（毫秒） | 0.95080 | 0.87400 | 8.08% |
| BENG TOKENIZE（毫秒） | 0.82755 | 0.73950 | 10.64% |
| 中文查询（毫秒） | 5.18800 | 5.07465 | 2.18% |
| 英文查询（毫秒） | 6.96680 | 6.83930 | 1.83% |
| 混合查询（毫秒） | 5.79120 | 5.39865 | 6.78% |
| LIMIT 查询（毫秒） | 6.87535 | 6.21260 | 9.64% |

按赛题的分组平均方式，建索引改善 4.47%，分词改善 9.36%，查询改善 5.11%，
综合改善 6.31%。这里的 baseline 是本地相同代码基线的实测值，不是评分脚本中的
冻结 CI 基线，不能据此推算平台成绩。

测量限制：两次基线 SELECT 1 分别为 0.5631、0.6287 毫秒，优化版本分别为
0.6336、0.5972 毫秒，显示客户端循环/虚拟机调度有波动。首轮 BENG TOKENIZE
从 0.7197 变为 0.7320 毫秒，存在 1.71% 退化；第二轮基线为 0.9354 毫秒，
明显高于首轮。因此，BENG 分词均值收益和查询中较小的收益仍需官方环境复核，
本地结果不构成统计显著性结论。IK TOKENIZE 两轮均有改善。
